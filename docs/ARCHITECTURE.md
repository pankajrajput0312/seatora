# Architecture

## Overview
A modular monolith in one Next.js App Router application. Layers depend downward only:

```
src/app (routes)  →  src/features/* (domain)  →  src/lib (db, utilities)  →  external (Postgres, sources)
        ↘ src/components (shared UI, no domain logic)
```

## Folder structure
```
src/
  app/                 Routes, layouts, route handlers. Thin: fetch via feature services, render.
    (site)/            public pages: landing, about, pricing, policies, contact, login, signup, account
    decide/            the Decide app, one folder per screen (options, seats, …, residents, requests)
    api/v1/            the read API (options, seats, allotments, rank-journey, …)
  components/
    ui/                Design-system primitives (Button, Input, Badge, SourceLabel)
    layout/            Container, SiteHeader, SiteFooter, MobileNav
    marketing/         Landing-page sections
    home-v2/           the /v2 landing preview
  features/
    decide/            Decide: data reads (service.ts, server/), components, lib (links, params, reach, term filters)
    auth/              accounts, sessions, the access gate's allowlist and owners
    funnel/            first-party funnel events, the device cookie and hashed IP, error groups and alerts (FUNNEL.md)
    requests/          Request a feature: the action, the owner's list, the form
    waitlist/          the waitlist form and action
    cutoffs/           rank formatting, the MCC import schema
    rank-predictor/    rank fit (historical matching only)
    residents/         the landing page's residents-by-rank finder (its data file is empty)
  lib/                 db client, cn, rate limit, site access
  types/               cross-feature types (provenance)
  config/              site config, business details
prisma/                schema, migrations, the MCC and residents importers
e2e/                   Playwright tests
```

Inside a feature, create these only when needed:
```
features/<name>/
  components/   feature UI
  services/     data access (server-only), the only place that calls `db`
  hooks/        client hooks
  lib/          pure domain logic (unit tested)
  validations/  Zod schemas
  types.ts
```
Features may import from `components`, `lib`, `types` and `config`. A feature imports another feature only through that feature's `services` or `lib`, never its components.

## Routing conventions
- Public routes are `/` (landing), `/privacy`, `/login`, `/signup` and `/account`.
- **Exam landing pages** `/neet-pg`, `/neet-ss`, `/neet-mds`, `/ini-cet` (`src/features/exams/landing`: one server component, each exam's words in `words.ts`, its counts, examples and round status read live through the catalog and services in `data.ts`). The registry's per-exam `public` is the one switch: a public exam's page is static (hourly), indexable and in the sitemap; any other is staff only (OWNER, ADMIN, `gate.ts`), noindex, not in the sitemap, and a normal 404 for everyone else (its `<head>` the site's default). Only NEET PG is public. Server components only, so no exam's words or data are in a public JS chunk.

## Server and client boundaries
- Server Components by default. They fetch through `features/*/services`.
- Client Components (`"use client"`) are only for interactivity: filters, tabs, forms and charts. They receive serialisable props and never import `@/lib/db`, which is enforced by `server-only`.
- Charts are client components in a feature folder (Decide's are hand-written SVG in `components/charts.tsx`).

## Services and API conventions
- Services are plain async functions, for example `listColleges(filters)` and `getCollegeBySlug(slug)`. They return typed domain objects with provenance attached.
- During the demo-data phase a service may read a local typed dataset. Swapping in Prisma is then a change inside the service only. The UI must still label demo data.
- Mutations use Server Actions with Zod-validated input. Route handlers (`app/api/*`) exist for client components that fetch, external consumers (a future mobile app) and webhooks; Server Components call services directly. Exception: Choices relabels a whole list (hundreds of ids) through the Zod-validated Server Action `liveReach` (`app/decide/choices/actions.ts`), because `/api/v1/options/compare` takes at most 4 ids.
- Action and handler results are `{ ok: true, data } | { ok: false, error }`. Do not throw across the client boundary.

## Database access
- The Prisma client is a singleton in `src/lib/db.ts` and is imported only by services.
- Schema changes go through `npm run db:migrate`, and the schema documentation in `docs/DATABASE_SCHEMA.md` is updated in the same change.
- Pages and builds must not require a database until a feature actually reads from it.

## Authentication
Email and password, with no auth library (`src/features/auth`):
- Passwords are hashed with Node `scrypt` and a per-user salt (`lib/password.ts`).
- Sessions are database rows keyed by the SHA-256 of a random 32-byte token. The token lives only in an httpOnly, SameSite=Lax cookie (`medpath_session`, 30 days, Secure in production).
- `getCurrentUser()` is used in server components. Protected pages call it and `redirect("/login")`. The landing page stays static, so the header always shows "Sign in". `/login` and `/signup` send a user who already has Decide access on to `?next=` (see "Access gate"); anyone else sees the form.
- Sign-in and sign-up actions are Zod-validated and rate-limited per IP, and sign-in returns the same error for an unknown email and a wrong password.
- Sign-in always runs scrypt (against a dummy hash for unknown emails), so timing reveals nothing. Password guessing is limited at two levels: 5 failures per 15 minutes for each account and IP pair (in memory), which stops one attacker without locking the real user out elsewhere, and 20 failures on an account from any IP, which locks it for 15 minutes. That second counter is incremented atomically in the database, so parallel guesses can't race past it. At most 4 scrypt runs happen at once per instance (each uses about 128MB).
- Password reset without email (`lib/reset.ts`): "Forgot password?" on /login opens /forgot (write from the account's email to NEXT_PUBLIC_CONTACT_EMAIL, or WhatsApp with NEXT_PUBLIC_CONTACT_WHATSAPP); the owner makes a link with "Create reset link" in /decide/admin's Accounts (an AdminAudit row, `password_reset_link`). The link is one-time and an hour long, only its SHA-256 is stored (`PasswordReset`), a newer link voids the older; /reset?token= sets a password with sign-up's rules, deletes every session and link of hers and signs this browser in. /reset's views and submits share 10 tries per IP per 15 minutes.
- Not built yet: email verification (invite only: sign-up needs the invite code instead; open access: anyone signs up, with a per-IP limit; see "Access gate"), OAuth, and "sign out everywhere". These need an email provider; add them before accounts hold anything valuable.

## Access gate
Marketing and policy pages, `/login`, `/signup`, `robots.txt`, `sitemap.xml`, icons and the OG image are public. `/decide/**` and `/api/v1/**` are for signed-in members only (`src/middleware.ts`, logic in `src/lib/site-access.ts`, server checks in `src/features/auth/lib/session.ts`). Who is a member is one switch:
- **Open access** (`SEATORA_OPEN_ACCESS=1`, `openAccess()`; the free product): anyone may sign up (no invite code, no allowlist; the form hides the code field) and every signed-in account is a member, Residents' names included. Only `SITE_ACCESS_SECRET` is needed; `SEATORA_ALLOWED_EMAILS` and `SEATORA_INVITE_CODE` are ignored. Sign-up refuses an address on `SEATORA_OWNER_EMAILS` ("This email can't be used to sign up."), since nothing verifies emails: the owner's account is made before, or in closed mode. Sign-ups reaching the database are limited to 5 per IP per hour (in memory, on top of 30 a minute per IP); sign-in limits and lockout, the residents read budget and Hide are unchanged. The cookie key is `<secret>|*open*`, so switching the mode either way voids every access cookie. The privacy notice and `/signup` copy follow the switch at build time (they are prerendered or read it per request); the middleware and actions read it per request. Unset (anything but `1`): the invite-only mode below, unchanged.
- **Allowlist** (invite only): `SEATORA_ALLOWED_EMAILS`, comma-separated (trimmed, lowercased, empties ignored). Sign-up succeeds only for an allowlisted email **and** the `SEATORA_INVITE_CODE` (16+ characters, compared as SHA-256 digests; unset or short closes sign-up), because no email is verified: the address alone would let anyone who knows it claim the account. Anything else gets one message for both cases ("That email and invite code don't match an invite.") and nothing is created. Unset the code once the account exists. Sign-in with a wrong password is unchanged (one generic error, the same rate limits and lockout); a correct password on an account that isn't allowlisted returns "This account doesn't have access." and creates no session.
- **Signed in = member:** `getCurrentUser()` returns null for an account that isn't a member (`isMember()`: anyone in open mode, else on the allowlist), so sessions from before the lock (or of an email since removed) count as signed out everywhere, `/account` included.
- **Cookie:** a member's successful sign-in or sign-up also sets `seatora_access` = `<expiry>.<userId>.<HMAC-SHA-256 of "site-access:<expiry>:<userId>">` (httpOnly, Secure in production, SameSite=Lax, Path=/, 30 days like the session); sign-out deletes it. The HMAC key is `SITE_ACCESS_SECRET` (32+ random characters, `openssl rand -hex 32`) + `|` + the normalised, sorted allowlist (open mode: `*open*`), so neither expiry nor user can be changed, and a new secret or allowlist voids every cookie. Checked in constant time with Web Crypto, so it runs at the edge.
- **Middleware** (`src/middleware.ts`; matcher: every page and route handler but `_next/`, `/api/` other than `/api/v1` and files with an extension, plus all of `/decide`) sets the `seatora_aid` device cookie where missing (docs/FUNNEL.md) and, on `/decide/**` and `/api/v1/**` only, checks the access cookie. Without a valid one, pages get `307` to `/login?next=<path and query>` and the API gets `401 { ok: false, error: { code: "unauthorized" } }`. `/login` and `/signup` follow `next` only to a same-origin path (exactly one leading `/`; never `//`, `/\`, a backslash, whitespace or control characters; resolved with `new URL`, so dot segments can't make `//host`, and returned percent-encoded), else `/decide`.
- **Fail closed:** in production, a missing or short secret, or (invite only) an empty allowlist, denies every private path (pages: `/login?error=unavailable`; API: `503 access_unconfigured`) and logs one error; public pages keep working. Setting only one of them, or a short secret, does the same in development. With neither set in development the private paths are open and the middleware warns once.
- **Defense in depth:** `hasSiteAccess()` = a valid cookie, and `getCurrentUser()` (so a member) is that cookie's user (false whenever the gate isn't on, even in development). Server Actions can be POSTed to any route (e.g. `POST /` with a `Next-Action` header), past the matcher, so every Decide action checks for itself: `liveReach` through `canUseDecide()` (what the middleware would allow), the hide action through `canSeeResidents()`. The auth and waitlist actions are public.
- **Residents (names)** need `canSeeResidents()` (= `hasSiteAccess()`) in the pages (the institute tab, `/decide/residents`), `GET /api/v1/colleges/{slug}/residents` and the hide action, so removing the middleware can never make them public, and they stay hidden in development with the gate off. Reads (`residentsDenied("read")`, one per page or API call) are limited to 300 per hour per IP (in memory, per instance) and to the plan's residents reads per account per IST day (Free 10, Premium 200: `checkAndCount` in `features/plans`, `UsageDaily`, one atomic upsert, so a copied cookie gains nothing from new IPs or parallel instances; see [PLANS_AND_ROLES.md](PLANS_AND_ROLES.md)); hides to 20 per hour per IP. Hiding covers the person: every row with that name at a college with that PIN code, recorded in `HiddenResident` (no foreign key) so it survives re-imports and college key changes. Across colleges there is no JSON API (it would be the easiest interface to page through): only the page, through `server/residents-all.ts` `listResidentsAll(query)` (query and row types: `residents-search.ts`), which checks access and spends one read itself, then returns one page of 50, never past page 20 (`RESIDENTS_MAX_PAGE`; the page says to narrow the filters, and sends a deeper or stale page number to the last page served).
- **Names in URLs (accepted):** the Residents Name filter is a GET form like every Decide filter, so a typed name sits in the URL (`q=`): in browser history, the hosting platform's request logs, and, signed out, the `/login?next=` redirect. Nothing else carries a name; move the search to a POST or the client if that stops being acceptable.
- **Headers:** private responses are `Cache-Control: private, no-store` (overriding the pages' and API's `s-maxage`). `X-Robots-Tag: noindex, nofollow` only on `/decide`, `/api`, `/login`, `/signup` and `/account` (`next.config.ts`), and `robots.txt` disallows the same paths.
- Not built: revoking one cookie before it expires (sign-out deletes it in that browser; rotate `SITE_ACCESS_SECRET` to void them all), and the middleware can't see a deleted session, though every names read checks the session in the database.

## Validation
Zod is the single validation layer:
- Forms use React Hook Form with `zodResolver`.
- Search params are parsed with Zod; invalid params fall back to defaults instead of failing.
- Ingested datasets are validated with `provenanceSchema` plus a record schema, and invalid rows are rejected and reported, never silently fixed.

## Funnel and errors
First-party, in Postgres, no third-party SDK ([FUNNEL.md](FUNNEL.md)): `track()` (server, written after the response) and `POST /api/events` (the browser's whitelisted events by `sendBeacon`, identity from cookies only) fill `FunnelEvent`; sign-up is capped per device (`SIGNUP_PER_DEVICE`); `src/instrumentation.ts` `onRequestError` and the `error.tsx` boundaries group errors in `ErrorGroup` and post new ones to `ALERT_WEBHOOK_URL`.

## Error handling
- Expected failures (not found, invalid input) return typed results or call `notFound()`.
- Unexpected failures are caught by `error.tsx` boundaries and shown as the design-system error state, with a retry option; the boundary reports the error (message, digest, path) to `/api/events`.
- Log on the server; server errors are also grouped by `onRequestError` (docs/FUNNEL.md "Errors"). Never show stack traces or raw error output to users.

## Testing strategy
- **Vitest**: pure logic in `features/*/lib`, validations and formatting. Colocate as `*.test.ts`.
- **Playwright**: one smoke test per route, plus critical interactions (filters, compare, forms), on both desktop and mobile projects.
- `e2e/decide.spec.ts` runs on the real MCC import and asserts its spot values (skipped without `DATABASE_URL`). Set `PLAYWRIGHT_BASE_URL` (e.g. `http://localhost:3191` after `next build && next start -p 3191`) to run it against a started server instead of `npm run dev`. `e2e/smoke.spec.ts` writes to the database (waitlist, sign-up).
- Data-integrity rules get explicit tests, for example that missing values render "—" and that predictions are always labelled historical.
- **Loading and caching:** every /decide route has a `loading.tsx` shimmer skeleton (`components/skeleton.tsx`), so pages stream (a page-level `notFound()` then answers 200 with the not-found view and noindex). Seat lists, notices and merit lists are cached per process with `perImport()` (`server/catalog.ts`), invalidated by the import marker.
