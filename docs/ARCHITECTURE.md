# Architecture

## Overview
A modular monolith in one Next.js App Router application. Layers depend downward only:

```
src/app (routes)  →  src/features/* (domain)  →  src/lib (db, utilities)  →  external (Postgres, sources)
        ↘ src/components (shared UI, no domain logic)
```

## Folder structure
```
src/
  app/                 Routes, layouts, route handlers. Thin: fetch via feature services, render.
    (site)/            public pages: landing, about, pricing, policies, contact, login, signup, account
    decide/            the Decide app, one folder per screen (options, seats, …, residents, requests)
    api/v1/            the read API (options, seats, allotments, rank-journey, …)
  components/
    ui/                Design-system primitives (Button, Input, Badge, SourceLabel)
    layout/            Container, SiteHeader, SiteFooter, MobileNav
    marketing/         Landing-page sections
    home-v2/           the /v2 landing preview
  features/
    decide/            Decide: data reads (service.ts, server/), components, lib (links, params, reach, term filters)
    auth/              accounts, sessions, the access gate's allowlist and owners
    requests/          Request a feature: the action, the owner's list, the form
    waitlist/          the waitlist form and action
    cutoffs/           rank formatting, the MCC import schema
    rank-predictor/    rank fit (historical matching only)
    residents/         the landing page's residents-by-rank finder (its data file is empty)
  lib/                 db client, cn, rate limit, site access
  types/               cross-feature types (provenance)
  config/              site config, business details
prisma/                schema, migrations, the MCC and residents importers
e2e/                   Playwright tests
```

Inside a feature, create these only when needed:
```
features/<name>/
  components/   feature UI
  services/     data access (server-only), the only place that calls `db`
  hooks/        client hooks
  lib/          pure domain logic (unit tested)
  validations/  Zod schemas
  types.ts
```
Features may import from `components`, `lib`, `types` and `config`. A feature imports another feature only through that feature's `services` or `lib`, never its components.

A value that is not declared (or in words only, or an unknown bond status, or years not stated) is left out, and counted, unless `nd=keep`. No bond (`bondyrs=0`) lists only rows whose record says no bond (one adding that a state law's service may apply counts as not declared, so `nd=keep` lists it). An NBEMS maximum fee or minimum stipend passes a cap it is inside; outside it the college's own figure is unknown (never a fail); so too a basic stipend "+ DA" under a floor, and a fee Seatora took the GST off (`Figure.declared`) when the cap lies between the two figures. A type filter never passes a college without a type. Absent `maxfee` / `bondyrs` are her profile's caps on every page with the filters and on their CSVs and the Options API (a "Your cap" chip each; `any` lifts one). Results pages take `layout=cards|table` (ViewToggle; never `view`): with it (or the toggle's `medpath.view.<page>` cookie, `server/view.ts`) the server renders that view only, without it both (CSS picks one by width).
- Filter and search state lives in URL search params, so it can be shared and works with the back button. Parse params with Zod in `page.tsx` (`parseSearchParams(schema, params, lists)` in `features/decide/lib/params.ts`: a bad field falls back, ranks accept "30,000"). Filter forms are GET forms (`next/form`, `FilterBar`). A page's own filters never reuse a profile key (hence `aq`, `acat`, `lcat`, `lquota`), or they would leak into her profile on the next link.
- Every link between Decide screens comes from `decideLinks(params)` (`features/decide/lib/links.ts`; `useDecideLinks()` in client components). It keeps the profile params, with repeated values kept (`sp=A&sp=B` becomes `sp=A,B`); `L.with(path, changes)` keeps the page's filters too, `L.page(path, n)` changes the page.
- Lists are paginated on the server (`page`, 25–50 rows): service list functions take an optional `{ page, pageSize }` and return `{ rows, total, page, pageSize }`; pages render `Pager`, never a whole table. Options is the exception: 25 server-rendered rows plus a client "Show N more" that appends the next page from `/api/v1/options` and moves focus to the first new row (`page` is still honoured).
- **Profile in the URL:** the Decide profile (rank, category, PwD, specialties, degrees, optional exact courses `pairs`, quotas, states, max fee and max bond) is saved in localStorage under `medpath.profile` and mirrored into URL params (`rank`, `cat`, `pwd`, `sp`, `deg`, `c`, `quota`, `st`, `fee`, `bond`; list params repeated or comma-joined). `c` holds exact courses as `degree~SPECIALTY` (`c=DNB~FAMILYMEDICINE`); when present they replace specialties x degrees (which then only name her specialties), so "DNB Family Medicine only" can be said. Every course filter goes through `profileHasCourse(profile, { degree, specialty })` (SQL readers: `profileCourseFilter`, listSeats `pairs`); reach labels are on all her seat categories together, and an option row (Options, Choices, institute Courses, Options CSV) notes a seat list whose seats there are all on seat categories with another label of their own (`seatsBelow`), the label Seats shows on those rows; Options and Seats show one exact-course filter (`c`) instead of Course and Degree when the profile has pairs. The dialog ticks degrees per specialty and saves the old form when it can (`coursesFromPicks`), so profiles without pairs are unchanged. URL params override the saved profile. Every localStorage value is Zod-validated on read (choice lists item by item, so one bad entry never costs the rest). `DecideShell` adds the saved profile to the URL when it's missing and carries the params on every sub-nav link, so all Decide pages are server-rendered from the URL. Choice lists (`medpath.choices`) and the compare tray (`medpath.compare`) stay on the device.
- **Decide data:** pages call only `src/features/decide/service.ts`, which reads Postgres (the MCC import, `prisma/import-mcc.ts`) through `src/features/decide/server/`: `catalog.ts` keeps colleges, courses, sources, terms and the option list in memory per process (re-checked against the data version, one primary-key read per request, so it is never older than the cutoffs it labels), and `queries.ts` filters cutoffs and allotments in SQL per call (course, degree, state and college become CollegeSpecialty ids; year, round, quota, category and rank ranges go into the WHERE). There is no demo data at runtime: without `DATABASE_URL` (or with the database down) every service call throws `DataUnavailableError` and Decide shows "Data unavailable" inside its shell (the API answers 503 `data_unavailable`). Unit tests run the same service on the fixture `test/decide.demo.ts` through `setTestCatalog()`. Provenance comes from the data: `DataSource` lists the MCC result PDFs a block uses (Provisional while `DataSource.provisional`), and every fee, stipend, bond and penalty term carries its own source document. Terms are read into numbers in one place, `server/terms.ts` (`ProgrammeTerms` per programme offered: fee and stipend by year, whole-course fee, bond status and basis, years, amounts, leaving and other penalties for that programme, MCC's Round 2 forfeit, numbered sources with the MCC profile id and how many institutes cite that profile); pages only render that shape (`components/fees.tsx`), and every Options, Seats and Allotments row carries its course's (`fees`). A programme reads only its own bucket (MD: MD/MS, Diploma, MCh, MPH; DNB: DNB, NBEMS Diploma; `bucketOfDegree`, which `programOf` is), never the other one; MCh and MPH never take the MD/MS fee or stipend. BOND and PENALTY come from their verified record (`CollegeTerm.details`, validated by `bondDetailsSchema` / `penaltyDetailsSchema` in import-schema.ts: status documented / no_bond_verified / state_rule / no_bond_rule / unknown, `by_course` for MD/MS vs Diploma and DNB vs NBEMS Diploma, `by_subject`, penalty items); bond years come from a number in the record, else the head of the bundle's bond text ("Service bond: 2 years · …", "State bond: 3 yrs (diploma 2 yrs) …", "3 years (diploma 2)"), never from other words ("3 years of study"), with years joined on in its head clause added up and shown as such ("1 yr compulsory govt service + up to 3 yrs if called": 1 + 3 = 4); a state rule beside the college's document (`details.state_rule`, the newer) gives the rule's years; who a record row is for comes from its label (`groupOf`: DNB and DrNB are degrees, "NBEMS Diploma" the diploma, "DNB/Diploma" and PG labels that also name DM/MCh cover both); a leaving item owed on top of another ("lapse of the PG seat (additional)") adds to the figure; "no bond" keeps what the record is unsure of (`caveat`: a hospital taken as private from its name; a no-bond document adding that a state law's compulsory service may apply is status `not_declared` with that `caveat`, shown as "Unknown" with "state law may apply");
a state rule that gives the years gives its amounts too (`state_rule.amounts`, cited to the rule; `yearsFrom: "state_rule"`); bond and leaving amounts priced by clinical vs pre/para-clinical subject give the course's own figure (Pathology, Microbiology and any course in neither list keep the range, `varies`); a forfeit item with no figure and no quote takes the fee record's own words; FEE and STIPEND (bundle schema 2) come from the programme's fee-table records (FeesStructured; `catalog.ts` attaches the college + program's records to its FEE and STIPEND terms, as the bundle's `details.records`), the first in All India, Deemed/Paid, NRI, DNB Quota order: a fee only from a `fee_display` "numbers" record, each year as stated (a year not stated is null, never year 1's figure; an amount paid at admission is `atAdmission`), the whole course only as the record gives it, an NBEMS ceiling `maximum` and floor `minimum`; a "verbatim" record (or one without `fee_display`) gives no fee figure but its `fee_parsed` ones (INR only, `fromText` with the quote; year 1 with none: the amount at admission), with "see text"; the Round 2 forfeit falls back to the record's MCC form field; an older import's fee declared as a range (by subject) is a min–max whose highest figure caps and sorts; a state order or NBEMS rule is named as the record names it (title and date); an MCh reading a record whose rows are all for PG seats gets `other_course`. Only an older import's fee and stipend texts (no fee table) are read with regexes; a bond or penalty without its record (an import older than the records) is shown as published. The Fees page links each row's "Year by year" to the institute's Fees tab (no hidden copy per row). Bundle schema 2 is read through `queries.ts` (allotment rows carry `status` and the `remark` derived from it: Allotted, Fresh or Upgraded, `candidateCategory`, `optionNo` and `prev`, the seat printed one round back with its remark), `service.ts` `rankJourney(year, rank)` (one rank's allotments round by round, with names of the seats) and `server/facts.ts`: `clinicalFactsFor(collegeKey)` and `feesFor(collegeKey, programme)` (seat-type groups in All India, Deemed/Paid, NRI, DNB Quota order; `fee.display` "numbers" carries the year figures, "verbatim" (also an export without `fee_display`) only the profile's words and their link, never a figure). The one person-level table is `Resident` (names from MCC's admitted-candidates lists, private import; ranks 2023-2025 from that year's NBEMS NEET PG result, quota and round from the matching MCC allotment, minority quotas shown as "Minority", no category): it is read only through `src/features/decide/server/residents.ts` and `server/residents-all.ts`, behind `canSeeResidents()` (see "Access gate"). MCC's public allotment results list a category per rank; Seatora never joins them to names (DATA_INTEGRITY "Known inference").

Pagination `page`/`pageSize` (max 200). `Cache-Control: public, s-maxage=300, stale-while-revalidate=86400`.
- Use `loading.tsx`, `error.tsx` and `not-found.tsx` per route segment where meaningful. Every Decide route has a `loading.tsx` built from `components/skeleton.tsx` that mirrors its page's layout (title, filters, toggle, table or cards), so the shell and a shimmer show at once; a page's `notFound()` / `redirect()` then arrive after a 200 (not-found view, client redirect).

## Server and client boundaries
- Server Components by default. They fetch through `features/*/services`.
- Client Components (`"use client"`) are only for interactivity: filters, tabs, forms and charts. They receive serialisable props and never import `@/lib/db`, which is enforced by `server-only`.
- Charts are client components in a feature folder (Decide's are hand-written SVG in `components/charts.tsx`).

## Services and API conventions
- Services are plain async functions, for example `listColleges(filters)` and `getCollegeBySlug(slug)`. They return typed domain objects with provenance attached.
- During the demo-data phase a service may read a local typed dataset. Swapping in Prisma is then a change inside the service only. The UI must still label demo data.
- Mutations use Server Actions with Zod-validated input. Route handlers (`app/api/*`) exist for client components that fetch, external consumers (a future mobile app) and webhooks; Server Components call services directly. Exception: Choices relabels a whole list (hundreds of ids) through the Zod-validated Server Action `liveReach` (`app/decide/choices/actions.ts`), because `/api/v1/options/compare` takes at most 4 ids.
- Action and handler results are `{ ok: true, data } | { ok: false, error }`. Do not throw across the client boundary.

## Database access
- The Prisma client is a singleton in `src/lib/db.ts` and is imported only by services.
- Schema changes go through `npm run db:migrate`, and the schema documentation in `docs/DATABASE_SCHEMA.md` is updated in the same change.
- Pages and builds must not require a database until a feature actually reads from it.

## Authentication
Email and password, with no auth library (`src/features/auth`):
- Passwords are hashed with Node `scrypt` and a per-user salt (`lib/password.ts`).
- Sessions are database rows keyed by the SHA-256 of a random 32-byte token. The token lives only in an httpOnly, SameSite=Lax cookie (`medpath_session`, 30 days, Secure in production).
- `getCurrentUser()` is used in server components. Protected pages call it and `redirect("/login")`. The landing page stays static, so the header always shows "Sign in". `/login` and `/signup` send a user who already has Decide access on to `?next=` (see "Access gate"); anyone else sees the form.
- Sign-in and sign-up actions are Zod-validated and rate-limited per IP, and sign-in returns the same error for an unknown email and a wrong password.
- Sign-in always runs scrypt (against a dummy hash for unknown emails), so timing reveals nothing. Password guessing is limited at two levels: 5 failures per 15 minutes for each account and IP pair (in memory), which stops one attacker without locking the real user out elsewhere, and 20 failures on an account from any IP, which locks it for 15 minutes. That second counter is incremented atomically in the database, so parallel guesses can't race past it. At most 4 scrypt runs happen at once per instance (each uses about 128MB).
- Not built yet: password reset, email verification (invite only: sign-up needs the invite code instead; open access: anyone signs up, with a per-IP limit; see "Access gate"), OAuth, and "sign out everywhere". These need an email provider; add them before accounts hold anything valuable.

## Access gate
Marketing and policy pages, `/login`, `/signup`, `robots.txt`, `sitemap.xml`, icons and the OG image are public. `/decide/**` and `/api/v1/**` are for signed-in members only (`src/middleware.ts`, logic in `src/lib/site-access.ts`, server checks in `src/features/auth/lib/session.ts`). Who is a member is one switch:
- **Open access** (`SEATORA_OPEN_ACCESS=1`, `openAccess()`; the free product): anyone may sign up (no invite code, no allowlist; the form hides the code field) and every signed-in account is a member, Residents' names included. Only `SITE_ACCESS_SECRET` is needed; `SEATORA_ALLOWED_EMAILS` and `SEATORA_INVITE_CODE` are ignored. Sign-up refuses an address on `SEATORA_OWNER_EMAILS` ("This email can't be used to sign up."), since nothing verifies emails: the owner's account is made before, or in closed mode. Sign-ups reaching the database are limited to 5 per IP per hour (in memory, on top of 30 a minute per IP); sign-in limits and lockout, the residents read budget and Hide are unchanged. The cookie key is `<secret>|*open*`, so switching the mode either way voids every access cookie. The privacy notice and `/signup` copy follow the switch at build time (they are prerendered or read it per request); the middleware and actions read it per request. Unset (anything but `1`): the invite-only mode below, unchanged.
- **Allowlist** (invite only): `SEATORA_ALLOWED_EMAILS`, comma-separated (trimmed, lowercased, empties ignored). Sign-up succeeds only for an allowlisted email **and** the `SEATORA_INVITE_CODE` (16+ characters, compared as SHA-256 digests; unset or short closes sign-up), because no email is verified: the address alone would let anyone who knows it claim the account. Anything else gets one message for both cases ("That email and invite code don't match an invite.") and nothing is created. Unset the code once the account exists. Sign-in with a wrong password is unchanged (one generic error, the same rate limits and lockout); a correct password on an account that isn't allowlisted returns "This account doesn't have access." and creates no session.
- **Signed in = member:** `getCurrentUser()` returns null for an account that isn't a member (`isMember()`: anyone in open mode, else on the allowlist), so sessions from before the lock (or of an email since removed) count as signed out everywhere, `/account` included.
- **Cookie:** a member's successful sign-in or sign-up also sets `seatora_access` = `<expiry>.<userId>.<HMAC-SHA-256 of "site-access:<expiry>:<userId>">` (httpOnly, Secure in production, SameSite=Lax, Path=/, 30 days like the session); sign-out deletes it. The HMAC key is `SITE_ACCESS_SECRET` (32+ random characters, `openssl rand -hex 32`) + `|` + the normalised, sorted allowlist (open mode: `*open*`), so neither expiry nor user can be changed, and a new secret or allowlist voids every cookie. Checked in constant time with Web Crypto, so it runs at the edge.
- **Middleware** (matcher `/decide/:path*`, `/api/v1/:path*` only) checks the cookie. Without a valid one, pages get `307` to `/login?next=<path and query>` and the API gets `401 { ok: false, error: { code: "unauthorized" } }`. `/login` and `/signup` follow `next` only to a same-origin path (exactly one leading `/`; never `//`, `/\`, a backslash, whitespace or control characters; resolved with `new URL`, so dot segments can't make `//host`, and returned percent-encoded), else `/decide`.
- **Fail closed:** in production, a missing or short secret, or (invite only) an empty allowlist, denies every private path (pages: `/login?error=unavailable`; API: `503 access_unconfigured`) and logs one error; public pages keep working. Setting only one of them, or a short secret, does the same in development. With neither set in development the private paths are open and the middleware warns once.
- **Defense in depth:** `hasSiteAccess()` = a valid cookie, and `getCurrentUser()` (so a member) is that cookie's user (false whenever the gate isn't on, even in development). Server Actions can be POSTed to any route (e.g. `POST /` with a `Next-Action` header), past the matcher, so every Decide action checks for itself: `liveReach` through `canUseDecide()` (what the middleware would allow), the hide action through `canSeeResidents()`. The auth and waitlist actions are public.
- **Residents (names)** need `canSeeResidents()` (= `hasSiteAccess()`) in the pages (the institute tab, `/decide/residents`), `GET /api/v1/colleges/{slug}/residents` and the hide action, so removing the middleware can never make them public, and they stay hidden in development with the gate off. Reads (`residentsDenied("read")`, one per page or API call) are limited to 300 per hour per IP (in memory, per instance) and to the plan's residents reads per account per IST day (Free 10, Premium 200: `checkAndCount` in `features/plans`, `UsageDaily`, one atomic upsert, so a copied cookie gains nothing from new IPs or parallel instances; see [PLANS_AND_ROLES.md](PLANS_AND_ROLES.md)); hides to 20 per hour per IP. Hiding covers the person: every row with that name at a college with that PIN code, recorded in `HiddenResident` (no foreign key) so it survives re-imports and college key changes. Across colleges there is no JSON API (it would be the easiest interface to page through): only the page, through `server/residents-all.ts` `listResidentsAll(query)` (query and row types: `residents-search.ts`), which checks access and spends one read itself, then returns one page of 50, never past page 20 (`RESIDENTS_MAX_PAGE`; the page says to narrow the filters, and sends a deeper or stale page number to the last page served).
- **Names in URLs (accepted):** the Residents Name filter is a GET form like every Decide filter, so a typed name sits in the URL (`q=`): in browser history, the hosting platform's request logs, and, signed out, the `/login?next=` redirect. Nothing else carries a name; move the search to a POST or the client if that stops being acceptable.
- **Headers:** private responses are `Cache-Control: private, no-store` (overriding the pages' and API's `s-maxage`). `X-Robots-Tag: noindex, nofollow` only on `/decide`, `/api`, `/login`, `/signup` and `/account` (`next.config.ts`), and `robots.txt` disallows the same paths.
- Not built: revoking one cookie before it expires (sign-out deletes it in that browser; rotate `SITE_ACCESS_SECRET` to void them all), and the middleware can't see a deleted session, though every names read checks the session in the database.

## Feature requests
Anyone can ask for a feature, a customization, a data correction or anything else (`src/features/requests`; contract in `validations.ts`, table `FeatureRequest`):
- `submitFeatureRequest` (Server Action, public like the waitlist, no sign-in needed): 3 a minute per IP in memory, then Zod, then the honeypot `website` (filled: pretend ok, store nothing). Signed in (`getCurrentUser()`), the row gets her `userId` and her email unless she typed another; signed out, an email is required so the owner can reply. Signed out, also 5 a day per IP in memory (never stored, as the privacy notice says). Counted in the database: 10 a day per account, and 100 a day for everyone signed out together as a backstop (its message gives the contact email). Messages are plain text, rendered only through React's escaping; failures log the error's code or name, never a message or email.
- **Owner:** `isOwner()` (`features/auth/lib/session.ts`) = a signed-in user with role `OWNER` (`User.role`; `SEATORA_OWNER_EMAILS`, comma-separated, bootstraps it: `getCurrentUser()` promotes those accounts, and the list stays a fallback). Open access never makes anyone an owner. `server.ts` (server-only): `listMyRequests()` (her own rows, newest first, 50), `listAllRequests({ status, kind, page })` (owner only, else null; 50 a page with `total`; bad filters are dropped; each row's `account` is the signed-in sender's account email, since `email` and `page` are whatever the sender typed, and the owner's list shows "Signed in as …" or "No account: email not verified"); `actions.ts` also has `setRequestStatus(id, status)` (owner only, checked in the action, Zod: `new | planned | done | declined`). Server Actions only, no API route.
- **UI** (`components/`): one `RequestForm` (kinds as radios, message with a live count, email: the account's read-only when signed in, required otherwise) on `/decide/requests` and in a section of the public `/contact` page (still static, no sign-in). `/decide/requests` (the sidebar's Help group, "Request a feature", its last item) adds "Your requests" and, for the owner only, "All requests" (`status`, `kind`, `page` filters; a status select per row that saves on change). Every Server Action of `actions.ts` is reachable from `/contact` too, which is why `setRequestStatus` checks the owner itself.

## Plans, roles and admin
`User.role` (OWNER, ADMIN, PREMIUM, FREE) and `User.premiumUntil` decide the plan (Free or Premium; `FREE_FOR_ALL_UNTIL` makes everyone Premium until then). Limits live in one table, `src/features/plans/plans.ts` (env overrides `PLAN_<PLAN>_<FEATURE>`); `usage.ts` `checkAndCount(userId, feature, key?)` counts per IST day in `UsageDaily` / `UsageDistinct`, server-side only. Enforced in the institute page and API (distinct institutes a day), Residents (reads a day), the CSV export routes (403 `plan_required`), Compare (cap), Ask (questions a day; `create_report`, `save_choice_list`) and the choices sync (saved lists). Over a limit a page shows the `Paywall` card (with the plan cards); the header's plan chip and the sidebar's account footer show her plan and link to `/decide/plan`. `/decide/admin` (owner and admin only, else not found): accounts, roles, Season Pass dates (audited in `AdminAudit`) and usage totals. `getCurrentUser()` is React-cached, so the layout, page and plan checks share one session read per render. Details: [PLANS_AND_ROLES.md](PLANS_AND_ROLES.md).

## Validation
Zod is the single validation layer:
- Forms use React Hook Form with `zodResolver`.
- Search params are parsed with Zod; invalid params fall back to defaults instead of failing.
- Ingested datasets are validated with `provenanceSchema` plus a record schema, and invalid rows are rejected and reported, never silently fixed.

## Error handling
- Expected failures (not found, invalid input) return typed results or call `notFound()`.
- Unexpected failures are caught by `error.tsx` boundaries and shown as the design-system error state, with a retry option.
- Log on the server. Never show stack traces or raw error output to users.

## Testing strategy
- **Vitest**: pure logic in `features/*/lib`, validations and formatting. Colocate as `*.test.ts`.
- **Playwright**: one smoke test per route, plus critical interactions (filters, compare, forms), on both desktop and mobile projects.
- `e2e/decide.spec.ts` runs on the real MCC import and asserts its spot values (skipped without `DATABASE_URL`). Set `PLAYWRIGHT_BASE_URL` (e.g. `http://localhost:3191` after `next build && next start -p 3191`) to run it against a started server instead of `npm run dev`. `e2e/smoke.spec.ts` writes to the database (waitlist, sign-up).
- Data-integrity rules get explicit tests, for example that missing values render "—" and that predictions are always labelled historical.
- **Loading and caching:** every /decide route has a `loading.tsx` shimmer skeleton (`components/skeleton.tsx`), so pages stream (a page-level `notFound()` then answers 200 with the not-found view and noindex). Seat lists, notices and merit lists are cached per process with `perImport()` (`server/catalog.ts`), invalidated by the import marker.
